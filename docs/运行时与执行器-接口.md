# 运行时与执行器接口契约

本文说明运行时 API 如何交接研究任务、研究 worker 如何续行，以及各角色如何调用执行器。运行时 API 与 worker 通过同一个 PostgreSQL 任务库交接。执行器是各进程内的函数调用，负责访问模型 API 或启动本机 CLI。工作台 [AG-UI](工作台-AG-UI.md) 和[发现 A2A](发现服务-A2A.md) 分别承载网页交互与服务间委托。

## 运行时 API 与研究 worker

| 阶段 | 输入、输出和身份 |
| --- | --- |
| 前台受理与决定 | 原生 Chat 的 `runId` 对应任务 ID，`threadId` 和末条用户消息 ID 对应 `conversationId` 和 `turnId`。运行时核对 `RuntimeTurnInput` 的原问题 `query`、原轮关系、`context`、模型 `config` 及可选的渠道设置。上下文与历史从服务端已采纳的事实生成。前台回复直接归档。用户在已核的原确认卡明确选择 `approve` 且不带补充文本时，直接沿用原提案，新增模型规划为零，仍复核实际目标。 |
| 交接后台步骤 | 同一事务将前台消息原 ID 提升为后台任务，并保存已验证输入和计划。`chat-research.v1` 包含 `body` 和规划记录 `plan`。其中规划记录的类型是 `runtime-turn-plan`，版本为 1，含 `inputFingerprint`、计划、已有过程与可选的轮次上下文。明确的观测请求、问题确认或研究澄清可以按各自校验路径直接入研究队列。 |
| 领取、续行与产出 | worker 持任务租约领取任务，根据原输入指纹和轮次身份复核交接计划，续行时再核对已绑定的来源。worker 保存业务进度和已读材料，按执行结果提交 `complete` 或 `failed`，用户取消由运行时单独提交 `cancelled`。持久的 `runtime-turn-step.v1` 检查点记录模型调用、原发现委托身份及进展、稳定编号和预算截止点。 |

研究 worker 的步骤租约为 15 秒，每 5 秒续期。事件、检查点和终态写入校验原任务的租约所有人和递增围栏号。等待原发现任务时保存检查点和原受理身份，再让出步骤租约。进程中断后，有检查点的原任务可再领取，缺检查点的中断任务标记 `worker_interrupted`。恢复时匹配输入与模式签名后复用已持久化的模型结果。结果仍未知的已启动模型调用不自动重发。未开始调用且模型名额已满时，后台可保存检查点后排队。原发现委托的重发判定见[只读恢复契约](发现服务-A2A.md#受理回执恢复)。

## 模型执行器

运行时的 `researchExecutor(...).model(prompt, options, signal)` 负责传入本轮已授权的模型选择、净化后的提示和输出约束。其内部模型调用为：

```ts
runExecutor(config: ChatModel, prompt: string, signal: AbortSignal, options?: ExecutorOptions): Promise<string>
```

| 项目 | 契约 |
| --- | --- |
| `config` | `executor` 取 `codex` 或 `claude`。选项含模型 `model`、`provider` 与自定义 `endpoint`。实际运行凭据从执行端读取。原生模式使用执行器已有授权。官方 DeepSeek 的运行时凭据由部署注入。设置页输入的 Key 只用于工作台读取模型列表。当前自定义兼容服务可读取列表，实际 Chat 模型使用执行器已有授权或部署端的官方 DeepSeek 凭据。 |
| `prompt`、`outputSchema` | 提示和可选模式先过安全校验。原生 Codex CLI 使用输出模式文件。各模型传输支持的约束不同，调用者仍须校验输出和业务动作。 |
| `publicText`、`providerReasoning` | `publicText.onDelta` 只对符合条件的前台 Flash 调用启用。推理摘要提供独立回调，只有通过公开投影的候选可以作为摘要展示。最终正文由业务调用者校验。 |
| `webSearch`、`singleRequest` | 原生搜索只允许有授权的原生 Codex，前台直连不启用供应商工具。符合条件的 Codex Flash 转发分支使用 `singleRequest` 约束一次上游调用。发现进程给自身规划传此选项。 |
| 返回与异常 | 成功返回文本。普通 CLI stdout 与前台 Flash 的正文各有 150,000 字符的应用级上限。结构、引用、权限和资料是否可交付由运行时判断。执行器可抛 `ExecutorFailure`，涵盖认证、限流、输入超限、超时、中止、输出超限、启动失败等类别。参数、凭据或模型容量问题也可在真正启动前失败。内部诊断不作为浏览器错误码契约。 |

| 角色与选择 | 实际执行 |
| --- | --- |
| 运行时前台，官方 DeepSeek Flash | 运行时凭据就绪、模型为 `deepseek-flash` 且供应方为 `deepseek` 时，直接调用固定官方 Responses 入口。单次调用无 CLI、上游工具、自动重试或回退。适配器的传输判定也识别端点恰为 `https://api.deepseek.com` 的 `custom` 形状，实际执行仍须先取得运行时凭据。 |
| 运行时后台，合格 Codex Flash | 通过本机 Codex CLI 和仅限本次调用的回环转发发送官方 Responses 请求。后台按调用最多一次上游请求。 |
| 其他支持的模型或角色 | 沿现有 Codex 或 Claude CLI 路径，每次执行启动一个受约束的子进程，提示从 stdin 发送。发现进程使用独立的 `ONEEARTH_DISCOVERY_CHAT_MODEL`，自己的模型调用串行安排。 |

真正的模型输出作为业务文本或候选结构返回。模型结果不能授予来源、工具或地图操作权限。原生 Codex 指定模型的摘要和发布边界见[原生 AG-UI](架构与接口现状.md#原生-ag-ui)。

## 名额和时限

| 资源 | 默认边界 | 用尽后的行为 |
| --- | --- | --- |
| 前台 Chat 受理 | 同一运行时库最多 4 笔 `planning` 状态，按原运行去重。 | 新受理达到上限时返回 HTTP 429 和 `Retry-After: 2`。 |
| 后台研究步骤 | 同一运行时库最多 2 个有效任务租约。`ONEEARTH_RUNTIME_STEP_CONCURRENCY` 可配置。每个研究 worker 同时领取一个步骤，正式部署有两个 worker。 | 现有队列保持待领。等待发现的已保存步骤让出租约，按原任务续行。 |
| 运行时模型 | 运行时库默认 3 个模型名额，其中 1 个只能用于前台。使用 `ONEEARTH_RUNTIME_MODEL_CONCURRENCY` 与 `ONEEARTH_RUNTIME_FOREGROUND_RESERVED` 配置。模型名额另有 15 秒租约和 5 秒续期，CLI 子进程发送提示前要绑定到有效名额。 | 未取得名额时不会发模型请求。持久后台步骤可排队等下一次领取。已受理前台运行的执行失败走原流的业务终态。 |
| 发现模型 | 发现进程有独立的模型队列，串行执行。 | 依原发现作业等待，受各调用时限和取消约束。 |
| 网页工具回调 | 运行时 API 独立队列默认同时执行 2 个工具。每次领取后的外层执行时限为 35 秒，具体提供方可更短。工具中的获准原生搜索还会使用运行时模型名额。 | 提交、进度、回执及错误按[内部工具契约](发现服务-A2A.md#公开网络工具的运行时执行)。 |

前台已受理运行的外层时限为 125 秒，前台规划最多调用模型 4 次且使用 110 秒决策预算。前台官方 Flash 的单次请求、CLI 子进程各有 110 秒上界，调用方传入更短的截止时间时会先中止。研究答复首稿和修订共享自己的 110 秒预算，每次提示最多 256 KiB UTF-8。取证动作及成文额度见[研究答复与证据降级](架构与接口现状.md#研究答复输入与证据降级)。这些是应用侧名额和截止时间，外部供应商的并发及限流另行生效。

## 取消、停止和重启

- 原生 SSE 断开只结束订阅。用户显式取消时，先由运行时数据库确认原任务的唯一取消终态。执行中的本地模型和工具收到相应中止。CLI 确认直接子进程已退出且调用已被中止时关闭本地管道，释放执行资源。
- 只有已持久的用户取消触发原发现委托的远端取消。运行时用已受理绑定或只读查证取得的原 Task ID 尝试停止。独立回执 `remoteStop` 可为 `pending`、`confirmed`、`unconfirmed`。`confirmed` 表示已验证远端终态，实际状态读取 `remoteState`。远端先完成时，本地取消终态保持，已保存材料仍可查。
- 已受理的前台规划若因运行时 API 重启中断，原消息终结为 `chat_interrupted`。后台 worker 更新时按原检查点恢复可续行步骤。正式的运行时、两个研究 worker、发现和时空角色使用独立 LaunchAgent。开发用多角色启动器在一个子进程退出时结束同组进程。

## 持久业务操作（隔离候选）

运行时为需要等待和续行的业务分配 `operationId`。研究条件的采用和清除仍通过 `/api/workspaces/:conversationId/actions` 进行单次事务。业务操作与 AG‑UI 轮次分别持有自己的状态，主动补答的新轮关联原操作。已有轮次的公开记录、HTTP 状态和 AG‑UI 终态继续使用其原 `runId`。

| 存储 | 作用 |
| --- | --- |
| `runtime_tasks` | `task_type=operation` 的记录使用原 worker 名额、租约和围栏。运行记录与内部操作分别读取。 |
| `runtime_operations`、`runtime_operation_runs` | 保存受理时的条件、原轮、当前关联轮和当前等待步骤。AG‑UI 终态可以先于操作完成。 |
| `runtime_steps`、`runtime_operation_steps` | 前者保留当前检查点，后者保存按操作排序的服务、用户或浏览器等待及事实回执。同一操作只有一个当前等待点。 |
| `runtime_model_budget_owners` | 已关联的执行任务累计到原轮的模型预算，执行名额仍按实际任务核验。新账目可区分实际执行任务。 |

运行时在发起服务步骤前保存请求 ID。恢复使用原检查点、原输入和原请求 ID。已知安全的覆盖读取可沿冻结的范围和发布版本续读。发现委托使用已核验的原 A2A Task 和水位。在同一个 PostgreSQL 事务内核对当前步骤、保存回执、唤醒原操作或排入已绑定的续答轮。取消关闭后继推进，后到的有效回执记入原步骤。相同回执可重传，内容冲突返回 409。

候选接入了发现委托补答和同轮目录上球两条业务。浏览器侧只持有实际动作的窗口权限，研究条件、已取数据和操作进度由运行时保存。影响当前动作的窗口变化由动作依赖判定。若窗口凭据随整页刷新丢失，可查看和取消原操作。原页面是否已经完成但尚未送达回执需要额外证据。

迁移为增量 DDL。已有任务类型默认为 `run`，旧记录沿原路径读回。若需回退到不识别业务任务的运行时，先停止新受理，核对或结束所有待续行的业务操作，再恢复原运行时；不要让旧 worker 领取候选里的内部操作。
